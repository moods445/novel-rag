# 小说RAG 全方案汇总（适配你的目标：整本小说上传、对接 OpenCode Agent、MCP 协议）
## 一、你的核心需求梳理
1. 用户侧：**一次性上传整本小说（TXT）**；内部可以拆解为章节分批处理，对外是一键导入。
2. 文本处理：自动识别章节边界（第X章），每一个切片携带元标签：`book_name`、`chapter_no`、`chunk_seq`（章节内块序号）。
3. 检索痛点：向量/图检索默认按相似度打分返回碎片，**碎片顺序是乱的，RAG底层不会自动还原剧情先后顺序**；必须在胶水层排序、拼接之后再交给大模型。
4. 上层调用：RAG作为独立外部服务，通过 **MCP Server** 封装，给 OpenCode Agent 调用，不在OpenCode内部重写RAG逻辑。
5. 能力需求：
   - 剧情细节问答；
   - 指定连续章节总结（例如前五章总结）；
   - 可选：人物关系、事件关联挖掘。
6. Embedding选型：**Qwen3-embedding-0.6b**，Cloudflare Workers AI 可直接调用，上限 8192 token（仅输入）。
   - Token参考：1个中文平均约0.3~0.4 token；1 token ≈ 2.5~3个中文字；
   - 切片安全策略：保守控制单块汉字，预留冗余，避免生僻字、标点挤占token。

## 二、可选底层RAG底座对比（三类路线）
> 重要前提：**下面所有底座都是通用RAG，没有原生小说时序/章节排序能力，排序拼接逻辑都要自己写在MCP胶水层**
### 路线1：传统向量RAG（纯向量检索，无图谱）
代表：RAGFlow、Dify、AnythingLLM
✅ 推荐：**RAGFlow**
- 优点：Docker一键部署，支持自定义元字段、REST API、可替换Embedding；混合检索（向量+BM25）；成熟稳定。
- 适合场景：需求以原文检索、章节总结为主，**很少深挖人物关系**；维护成本最低。
- 短板：没有实体关系图谱，查人物交互、事件关联容易漏信息。
- 改造点：前置脚本识别章节、打元数据；MCP层拿到召回结果后按 `chapter_no, chunk_seq` 排序拼接。

### 路线2：GraphRAG（微软图RAG）
✅ 优点：建库阶段抽取实体、关系、聚类社区，预生成社区摘要；**大范围跨章节全局总结、全书人物势力梳理效果最强**；适合一次性导入完结小说。
❌ 缺点：建库消耗海量token、速度慢；修订/重传全书基本需要全量重建；成本高。
适合：高频问全书主线、人物关系、全局梳理；能接受一次性高昂建库开销。

### 路线3：LightRAG（港大，轻量化图RAG）
✅ 优点：同样构建实体关系图谱；**索引token开销远低于GraphRAG，建库快**；双层检索（关键词+实体），查人物出场、局部剧情很稳。
❌ 缺点：没有预生成社区摘要；做大段跨章节总结，效果弱于GraphRAG。
适合：以细节问答、人物关联查询为主，全局总结只是偶尔使用；一次性导入完结本。

> GraphRAG vs LightRAG 一句话取舍：
> 想要很强的全书/多章节宏观总结能力、预算充足 → GraphRAG；
> 想要省钱、建库快、侧重人物细节检索 → LightRAG。

## 三、完整标准链路（最终落地链路）
```
整本小说TXT
    ↓【前置预处理脚本（你自己写）】
正则识别章节标题 → 切分章节 → 语义切块 → 给每个chunk打上元数据：book_name、chapter_no、chunk_seq
    ↓
送入RAG底座（RAGFlow / GraphRAG / LightRAG）入库、生成向量/图谱
    ↓【RAG底座：只负责检索，返回相似度排序的碎片】
外部RAG HTTP API
    ↓【MCP胶水服务（你自己写，核心层）】
MCP收到OpenCode的查询 → 请求RAG API拿到碎片 → 抛弃相似度顺序 → 按 chapter_no、chunk_seq 排序 → 拼接成连续有序文本 → 交给LLM生成回答
    ↓
OpenCode Agent（通过MCP协议调用这个知识库工具）
```
关键点：**时序还原的逻辑，全部放在MCP胶水层，而不是RAG底座，也不是OpenCode Agent内部**。

## 五、关键坑点汇总（反复强调）
1. Embedding 8192 token 是**输入上限**，向量输出不占用；中文不能按UTF-8字节估算token，按子词统计。
2. 任何主流RAG（RAGFlow、GraphRAG、LightRAG）召回顺序都是相关性优先，**不会自动按小说剧情先后排序**，这是通用RAG和小说叙事场景最大的鸿沟。
3. MCP在这里的定位：不是RAG本身，是**协议适配+后置排序拼接胶水层**，让OpenCode Agent以标准MCP工具方式调用外部RAG。
4. 不存在开箱即用、高星、专门面向长篇小说、自带章节时序逻辑的成品RAG服务，全部需要二次开发胶水代码。

## 六、最简选型推荐（给你二选一）
- 方案A（低复杂度优先）：RAGFlow + 预处理脚本 + MCP胶水
  适合：你主要就是查剧情、总结指定章节，人物关系需求不多，运维简单。
- 方案B（能力更强，复杂度更高）：LightRAG + 预处理脚本 + MCP胶水
  适合：经常要查人物互动、事件关联；不想承担GraphRAG昂贵的建库成本。
